02SYSTEM / DOMAIN

Seven objects that
own the rules.

The domain model is deliberately small. It contains the things that must stay consistent when a request is decided: the person, the device, the credential, the policy, the request, the session, and the record. Everything else is a projection, a cache, or an operational detail.

The cast

User is the aggregate root. A user can hold several devices and several credentials, but the identity is singular. Device is the endpoint that carries posture; PasskeyCredential is the authenticator material bound to that device. Splitting them matters because a device can be revoked while a credential record remains useful for audit, and a credential can be replaced without inventing a new device.

Policy is a versioned decision input, not a mutable setting. AccessRequest captures the ask and its approval state. Session captures the grant and its live trust score. AuditEvent captures what happened. The model keeps the ask, the grant, and the record separate because they have different lifetimes: a request can expire without a session, a session can be killed while its audit record survives, and an audit record must remain verifiable after the user is gone.

Why these boundaries

The boundaries follow the decisions the system has to make. A passkey assertion is verified against a credential, not against a user directly, because the credential is what the authenticator signs with. Device posture is attached to a device, not to a session, because posture changes while sessions are live. A policy is pinned to a session by id and version, because a later policy edit must not retroactively change the explanation for an earlier decision.

The model also keeps the Policy Administrator out of the class diagram. The administrator is a service role that carries out decisions; it is not a domain object with its own state. That is why the component view has a Policy Administrator and the domain view does not. The same is true of the risk scorer: it produces a score and reasons, but the score is an input to a decision, not an entity with a lifecycle.

Invariants worth testing

  1. A session always references exactly one user and one resource; both are required.
  2. A session may reference at most one access request. A direct allow has request_id = NULL.
  3. A credential belongs to exactly one device and one user; the user id is denormalised for owner lookup.
  4. An audit event may have session_id = NULL. Deleting a session must not delete its history.
  5. A published policy version is immutable. A decision records both the policy id and the version.
  6. A trust score is an integer in [0, 100]. The band is derived from the score and never accepted as input.
  7. KILLED is terminal. A repeated kill returns the existing result, not a new state.
Modelling choice

Resource is a first-class entity

A resource has a name, a kind (web or SSH), a host, and a sensitivity class. Keeping it separate from the request lets policy target a catalog entry rather than a free-form URL or hostname. An unknown resource is a hard gate, not a policy miss.

Modelling choice

Audit is not a child of session

The audit event carries a nullable session id and its own actor id. If a session is deleted, the event remains. If a user is deleted, the actor UUID remains as a historical reference. This is intentional denormalisation in service of evidence.

What is deliberately absent

The class model covers the access-control bounded context. SecureVault payloads, SSH certificate blobs, and policy version history are operational stores with different encryption and retention rules; they are described in the database and API pages rather than forced into this diagram. There is no Tenant class because the system is single-tenant. There is no KubernetesWorkload or Database class because those resources are out of scope.

Reading the cardinalities

The diagram uses the UML convention: the label at the far end describes how many instances of that class may relate to one instance of the near class. User 1 → 0..* Device means one user may have zero or more devices, and each device belongs to exactly one user.
