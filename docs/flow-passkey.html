05FLOWS / IDENTITY

A login that never
sends a secret.

The employee touches the authenticator, the authenticator signs a challenge, and the server verifies a public-key signature. The fingerprint never leaves the key. The login is still a policy decision: identity is necessary, but posture and context decide whether this is a normal Tuesday or an approval conversation.

What the ceremony proves

A WebAuthn assertion proves three things at once: the private key is present, the user verified locally, and the signature covers the server's challenge and origin. It does not prove that the device is healthy, that the user is in the office, or that the request is sensible. Those are the Policy Engine's job. The sequence keeps the two claims separate so a valid signature is never mistaken for a valid session.

The portal verifies the assertion before it calls the engine. A failed ceremony never reaches the risk scorer. That ordering matters for both security and latency: malformed or replayed assertions are cheap to reject, and the expensive decision path only sees cryptographic material that already passed.

The checks that are easy to skip

The signature is the headline, but most real failures are in the details around it. The challenge must be single-use and short-lived. The origin must match the RP ID exactly. The user-verification flag must satisfy the policy, not just the browser's preference. The counter must increase. The credential must belong to the claimed user, and the device must still be enrolled.

Privacy

The server never sees a fingerprint

The biometric match happens inside the authenticator. The server receives a signature over the challenge and a public key it already stored. There is no biometric template in the database, no fingerprint image in the audit log, and no shared secret to phish.

Recovery

Losing a key is not losing the account

Recovery is a separate ceremony with its own policy, rate limits, and audit trail. A Shamir rebuild lowers the next score by 12 points for 24 hours. The login path never quietly falls back to a password.

Where the score enters

After verification, the portal calls POST /v1/authorize with the subject, device, resource, action, and context. The engine runs the hard gates, scores the request, checks policy, and maps the result to a band. In the figure the result is 92 and ALLOW: a valid passkey on a compliant known device, on the office network, during working hours. The session is created with a 30-minute TTL and an audit obligation.

A different context changes the answer without changing the ceremony. A fresh credential, a new ASN, and an off-hours request can land in the approval band; a counter regression is a hard deny regardless of the arithmetic. The login page explains the difference in plain language: the passkey proved who you are, and the engine decided what this request may do.

NIST 800-63B alignment

The ceremony uses a phishing-resistant authenticator with user verification, a server-generated challenge, origin binding, and a signature counter. Recovery is treated as a separate authenticator lifecycle event, not as a password reset. The design does not claim FIDO certification.
