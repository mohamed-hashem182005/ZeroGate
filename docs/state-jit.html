A small machine
with a single-use grant.

The JIT state machine is intentionally boring. It exists to make the approval window auditable and to prevent an approval from becoming a standing entitlement. The hard parts are the guards, not the state names.

Why the states are separate

REQUESTED and PENDING are different because a draft is not yet in the queue. APPROVED is not access; it is a grant that has not been used. CONSUMED is the only state that proves a session was opened. DENIED and EXPIRED are both no-grant outcomes, but they carry different reasons and different UI copy.

The machine has no transition from DENIED or EXPIRED back to PENDING. A new attempt is a new request with a new id. That keeps the audit trail linear and prevents an approver from resurrecting an old decision.

The guards are the design

Every guard is checked server-side. A requester cannot approve their own request even if they craft the HTTP call directly. A request that expired while the approver was reading it cannot be approved. A policy published during the wait is applied at resolution. A grant that was consumed cannot be replayed.

Timeouts

Two clocks, two meanings

The 15-minute SLA bounds the wait for a human. The 30-minute grant bounds the access window after approval. They are independent: a fast approval does not extend the grant, and a slow approval does not shorten it below the policy ceiling.

Cancellation

Withdraw is not a denial

A requester can withdraw before approval. The request closes as EXPIRED with decision_reason = REQUESTER_CANCELLED; it is not a human denial and it does not count against the requester. The API exposes this as POST /v1/jit/requests//cancel.

Approved is not access

The only state that proves access is CONSUMED. An approved grant that is never used expires and is recorded as such. The UI must not tell the user “you have access” until the grant has been consumed by a real session.
