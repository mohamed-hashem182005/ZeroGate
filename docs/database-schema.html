04SYSTEM / SCHEMA

The tables behind
the decision.

The physical schema is PostgreSQL 16, split into two readable slices: identity and access. The users table is repeated because it is the join point. Every foreign key states its delete rule, and the audit table is protected by grants rather than convention.

FIG. 04A–04B8 tables9 delete rulesPOSTGRES 16

Conventions

  • Identifiers: UUID v7 in every table, generated by the application, so ids sort by time and do not leak row counts.
  • Time: timestamptz everywhere; the database stores UTC and the UI renders the user's local time.
  • Enums: PostgreSQL enum types for user_role, user_status, policy_effect, request_state, session_state, and event_type. Adding a value is a migration, which is the point.
  • Names: snake_case, plural tables, singular columns, explicit _at suffixes.
  • Secrets: no plaintext secret, private key, biometric, or payload is stored in these tables.

Delete semantics are part of the design

A foreign key without an explicit action is a latent incident. The schema states the rule for every edge. Identity records cascade because they have no independent meaning. History-bearing records restrict because deleting a policy or a resource would break the explanation of a past decision. Session links in the audit log are nulled because evidence must survive the session.

The audit chain

audit_events is the one table the application can only append to. The row carries a gap-free seq, the previous event's hash, and a payload hash. The verifier walks the chain from the genesis event and stops at the first mismatch. A deletion is detectable because sequence numbers skip; an edit is detectable because the next event's prev_hash no longer matches.

-- The application role may append, but never rewrite.
GRANT INSERT ON audit_events TO zg_app;
GRANT SELECT ON audit_events TO zg_auditor;
REVOKE UPDATE, DELETE ON audit_events FROM zg_app;

-- The chain is serialised by the insert order.
CREATE UNIQUE INDEX uq_audit_seq ON audit_events (seq);

Events are partitioned monthly and retained for one year. An export takes a consistent snapshot, verifies the chain before writing, and emits JSONL with the sequence number and both hashes. The verifier is a separate binary with a read-only role, so a compromised application cannot certify its own tampering.

Why the same table appears twice

The identity figure and the access figure are two views of one database. users is shown in both because it is the join point: identity reads it for login and device ownership, access reads it for request and session ownership. In a real deployment it is one table with one set of grants. The split is a reading device, not a second copy.

Beyond these slices

The certificate ledger, the vault payload store, and the policy-version history are separate stores with different encryption and retention rules. They are described in the SSH, JIT, and API pages. The access-control schema on this page never holds a private key, a vault plaintext, or a certificate blob.
