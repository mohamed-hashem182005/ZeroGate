Five zones, two gates,
one decision.

Nothing reaches a protected resource without passing a gate that asks the Policy Engine. The employee, the admin, the enforcement points, the decision brain, and the protected resources are separated on purpose: the gate enforces, the engine decides, the administrator acts, and the audit chain remembers.

The shape of the system

The source material describes five zones: the employee side, the enforcement points, the decision brain, the protected resources, and the admin side. The figure compresses those into three bands so the request path stays legible. The admin side sits with the employee clients because both are human-facing; the enforcement points and the decision brain share the control plane because they are one conversation.

The separation that matters is PDP versus PEP. The web proxy and the SSH certificate authority are Policy Enforcement Points. They hold no policy of their own and make no judgement about a person. They ask, then enforce. The Policy Engine is the Policy Decision Point. It combines hard gates, the risk score, and the published policy into one answer with obligations. NIST SP 800-207 calls for exactly this split; the trust algorithm itself is left open, which is why this project defines one.

Two paths, one decision

A web request and an SSH connection look different at the edge and identical at the centre. The web proxy authenticates the browser session, adds the request context, and calls POST /v1/authorize. The SSH authority receives a certificate request from the helper, authenticates the user and device, and calls the same endpoint with a different action and resource. Both receive the same decision shape: decision, band, score, signals, obligations, audit id, and correlation id.

That sameness is deliberate. It means one policy language, one explanation format, one audit record, and one place to fix a mistake. It also means the two paths can share the session cache at the enforcement point: a positive decision is valid for at most one second, and a kill invalidates it immediately.

The gate

Enforcement points never decide

The proxy and the CA are deliberately thin. They authenticate the channel, attach context, call the engine, and enforce the answer. If the engine is unavailable, they fail closed. If a cached decision is older than one second, they ask again.

  • No bypass path from the lab network.
  • No local policy exceptions.
  • No long-lived authorization cache.
The brain

The engine has one job

The Policy Engine evaluates hard gates before any arithmetic, then scores, then applies policy, then maps the result to a band. It returns obligations rather than side effects; the Policy Administrator carries them out.

  • Hard gates cannot be outvoted.
  • Every answer carries an audit id.
  • The same input returns the same answer.

Why the control plane looks like this

The Policy Administrator is separate from the Policy Engine because decisions and actions have different failure modes. A decision is a pure function of context, policy version, and model version. An action touches a live session, a proxy cache, a certificate, and a notification channel. Keeping them apart makes the decision reproducible and the action retryable.

The audit chain is separate from the operational database for the same reason. It is append-only, sequence-numbered, and hash-chained. The application role can insert but cannot update or delete. A reviewer can verify the chain without trusting the service that wrote it. The latency dashboard reads timings from the same event stream, so the performance claim and the security claim share one source.

What this figure does not show

The figure is a component view, not a deployment diagram. It does not show replicas, the HSM boundary, the lab network, or the observability stack. Those belong in a deployment view. It also does not show the stretch components: Single Packet Auth and SPIFFE/SPIRE service identity are deliberately absent from the main path so the core story stays honest.

Scope boundary

Only web applications and SSH servers are protected. Kubernetes, databases, email security, AI-agent governance, SWG, CASB, DLP, remote browser isolation, and firewall-as-a-service are out of scope. The system is single-tenant and lab-scale; there is no production deployment claim.

Failure posture

  • Engine timeout: deny. A late allow is worse than a false deny.
  • Risk scorer unavailable: rules-only score, with a visible MODEL_UNAVAILABLE reason and no ML adjustment.
  • Audit chain unavailable: fail closed for new sessions; never buffer decisions in memory and call them audited.
  • CA unavailable: no certificate; the helper prints an actionable reason and exits non-zero.
  • Proxy cache stale: at most one second; a kill invalidates it before the next request is admitted.
