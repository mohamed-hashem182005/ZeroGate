Trust is earned
in stages.

A device is not trusted because it exists. It is trusted because it was attested, bound to a user, and reported a passing posture. The state machine makes the stages explicit and makes revocation a one-step, terminal action.

FIG. 126 states9 transitionsPOSTURE ≤ 24 h

Why a device state machine

Posture is not a boolean. A device can be enrolled but not yet compliant, compliant but one report away from non-compliance, or quarantined while an admin investigates. The state machine gives the UI and the Policy Engine a shared vocabulary. It also makes the recovery paths explicit: remediation returns a non-compliant device to compliant; re-enrollment creates a new identity rather than reviving an old one.

Revocation is a one-way door

A revoked device cannot be un-revoked. The record stays in the database with its audit history, and a re-enrollment creates a new device id with a new key. That rule prevents a stolen device from being quietly restored by flipping a flag. It also means the admin UI must be clear: “revoke” is not “disable temporarily.”

Revocation cascades to the device's passkeys, live sessions, and SSH certificates. The proxy cache is invalidated, the CA revokes outstanding certificates, and the user is notified. The audit event records the actor, the reason, and the affected sessions.

Staleness

A report has a shelf life

A posture report older than 24 hours is a signal, not a fact. The device remains enrolled, but the risk score takes an 8-point deduction and the UI shows the age. A device that has not reported in 7 days is quarantined pending review.

Re-enrollment

New identity, old history

Re-enrollment issues a new device id and a new credential. The old record remains readable for audit. A session created under the old device id cannot be resumed under the new one; the user starts a new request.

What the agent does not collect

  • No file contents, browser history, clipboard, or screen capture.
  • No precise location; the server derives coarse network context from the request.
  • No biometric data; the passkey handles user verification locally.
  • No persistent device fingerprint beyond the enrolled id and posture fields.
A revoked device is not deleted history

The row remains, the passkeys remain as revoked records, and the audit chain remains verifiable. Deleting the device would break the explanation of every decision it participated in. The state machine is terminal, not destructive.
