09DECISION / ENGINE

Hard gates first,
arithmetic second.

The engine runs a fixed sequence: hard gates, score, policy, band. The order is not an implementation detail; it is the reason a stolen credential cannot be rescued by a high score. Every branch returns the same explanation shape, and every answer carries an audit id.

The algorithm

The engine is a pure function of context, policy version, and model version. It does not open sockets, revoke certificates, or write sessions. It returns a decision with obligations, and the Policy Administrator carries them out. That separation makes the decision reproducible and the action retryable.

function authorize(request):
    context = load(request.subject, request.device, request.resource)

    for gate in HARD_GATES:
        if gate.fails(context):
            return deny(gate, audit=True)

    score = risk.evaluate(context)           # rules + bounded ML
    policy = policies.match(context)         # pinned version
    if policy.effect == "deny":
        return deny("POLICY_DENY", score, audit=True)

    band = band_for(score)                   # 80 / 60 / 40 / 0
    decision = action_for(band, policy)
    return decision_with(score, reasons, obligations, audit_id)

The pseudocode is deliberately small. The complexity lives in the gate predicates, the signal catalog, and the policy matcher, not in a branching maze. A reviewer should be able to read the top-level order and know that a hard gate cannot be outvoted.

Why hard gates run first

A hard gate is a fact that makes the request invalid regardless of context. A revoked device is not a little bit risky; it is not eligible. An unknown resource is not a policy miss; it is not in the catalog. A counter regression is not a deduction; it is evidence of a cloned authenticator. Running the gates first means the score only ever ranks requests that are eligible to be ranked.

The same rule applies to an explicit policy deny. If the published policy says no, a score of 99 does not matter. The engine returns POLICY_DENY with the policy id and version, and the UI explains which rule matched. A deny is a decision, not an error.

From band to action

The band is a small state machine on top of the score. ALLOW creates a session with obligations. STEP-UP creates a challenge, not a session; the user re-authenticates within five minutes and the request is scored again. APPROVAL creates a JIT request and suspends the decision until a human resolves it. DENY / KILL creates no session and terminates any live one.

Determinism

The same input, the same answer

The decision records the policy id, policy version, model version, and input hash. Replaying the same inputs against the same versions produces the same decision, even if the current policy has moved on. That is what makes an audit review possible.

Failure posture

Fail closed, never open

A timeout, a missing policy, a malformed request, or an unavailable model all resolve to deny. A rules-only score is allowed when the model is down, but the decision is marked MODEL_UNAVAILABLE and the ML adjustment is zero.

What the engine does not do

  • It does not inspect packet payloads or file contents.
  • It does not open, proxy, or terminate a connection.
  • It does not train the ML model; it consumes a pinned version.
  • It does not decide resource sensitivity; that is a policy input.
  • It does not keep a long-lived authorization cache.
